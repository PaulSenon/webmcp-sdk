# D — Adversarial review of the release study

Observed **2026-11-11**. Verdict: **keep the security direction; do not implement these snippets verbatim**. Reviewed the six synthesis documents, A/B/C evidence notes, manifest/config/snippet checker, source and test structure. Repository observations below refer to initial HEAD `9e4a65e9f6749f3306fec0274be6386f80090627`; other agents subsequently edited the shared worktree. No installs, builds, publishing or account/settings mutations were performed. Public package archives were inspected in memory, without execution or extraction to disk. Only this file was created.

## 1. Verdict summary

- Stage-only OIDC plus npm-side human approval is a useful solo-maintainer control. It separates GitHub publication authority from npm approval authority; it does **not** independently establish that an artifact was honestly tested.
- There are two immediate release blockers: the stage job's path fallback exits under `pipefail`, and fresh finalization never obtains its release assets.
- Recovery needs a specified, cryptographically verified provenance contract. Reading repository/workflow strings from an attestation is insufficient; its package subject and digest must also match.
- GitHub release creation is not universally possible with `GITHUB_TOKEN` and `contents: write`: historical/prerelease targets with differing workflow files hit an additional permission restriction.
- PR-only admin bypass is real, but unnecessary for zero-approval solo PRs and also bypasses required checks. The proposed justification weakens the control it claims to provide.
- Current npm documentation already resolves two advertised unknowns: rejected versions can be re-staged; staging can create a package. Creating its **first OIDC trust configuration** remains a distinct bootstrap question.
- The source inventory is substantially accurate. React is implemented; source exports, aliases, absent build/publish machinery and source-based tests are real. Packaging validation is needed more urgently than monorepo restructuring.
- Several details are stale or mismatched to their pinned tools: download-artifact v8 fails digest mismatches by default; `rhysd/actionlint` is not a directly invokable action; the zizmor inputs do not implement the claimed offline/annotation mode.
- A single root library, separate private docs app when needed, native `tsc`, tarball consumers and a small staged-release workflow are sufficient. Mandatory relocation, two docs versions, extensive recovery automation and an extra approval environment need stronger cost/benefit justification.

## 3. Verified-correct load-bearing claims

- **npm stage invocation:** In npm **11.20.0**, `StagePublish` subclasses `Publish`. `--tag` and `--access` are accepted; inherited publish reads global `ignore-scripts`, and tarball input avoids directory lifecycle hooks. The proposed `npm stage publish ./pkg.tgz --tag … --access public --ignore-scripts` is valid. It must still be run from a clean configuration context. [Stage subclass][stage-subclass], [publish implementation][npm-publish].
- **Stage-only identity/provenance:** Current npm trust settings always allow staging while separately controlling direct publish and dist-tags. GitHub public-package OIDC enables automatic provenance in npm 11.20's shared publish path, including staging. `--provenance` is not required for this normal path. A local/session bootstrap is different. Node **26.13.0** really bundles npm **11.20.0**. [Trust settings][npm-trust], [OIDC implementation][npm-oidc], [bundled manifest][node-npm].
- **Rejected-stage reuse:** CLI docs explicitly prescribe rejecting then re-staging the same version when changing its fixed stage tag. This does not permit overwriting a version that was already published. Package creation by staging is documented; pre-creation OIDC trust setup is not thereby established. [Stage reference][npm-stage].
- **Registry endpoint and predicate:** A read-only fetch of `@standard-schema/spec@1.1.0` returned `dist.attestations.url = https://registry.npmjs.org/-/npm/v1/attestations/@standard-schema%2fspec@1.1.0`. Follow that metadata field on the allowlisted registry rather than inventing scoped escaping. Response shape is `{attestations:[{predicateType,bundle,…}]}`; one entry is npm publication attestation, another SLSA-v1 provenance. [Live metadata][spec-metadata], [live attestations][spec-attestations], [npm reader][pacote].
- **Exact SLSA-v1 fields:** Decode the selected bundle's DSSE payload; check `predicateType = https://slsa.dev/provenance/v1`. Workflow identity is under `predicate.buildDefinition.externalParameters.workflow.{repository,path,ref}`; commit under `predicate.buildDefinition.resolvedDependencies[].digest.gitCommit`, paired with its repository URI. `predicate.runDetails.builder.id` and `metadata.invocationId` identify runner/run. The package subject uses a PURL and **hex** SHA-512 digest, unlike SRI base64. These comparisons follow signature verification, not replace it. [npm 11.20 generator][provenance].
- **Tarball integrity:** npm 11.20 computes `dist.integrity` from the supplied compressed tarball bytes as `sha512-` plus base64 SHA-512. It does not hash the unpacked directory. The fetched spec tarball independently matched that calculation. Publishing an existing pnpm tarball therefore permits the proposed byte-equality check; do not compare it to upload-artifact's ZIP SHA-256. [Publish metadata construction][npm-libpublish], [live metadata][spec-metadata].
- **GitHub keys/conditions:** `cache-mode` is a real workflow/job key, including `none`; setup-node v7.1.0 has `package-manager-cache`; download-artifact v8.0.2 has `artifact-ids`. Environment selected-ref policy checks the run ref, including on dispatch. The finalize `always()` condition correctly allows recover mode despite skipped build/stage; skipped build outputs must be treated as unavailable, which the mode distinction already anticipates. [Cache reference][cache-docs], [setup-node][setup-node], [download source][download-src], [environments][env-docs], [job dependency semantics][workflow-syntax].
- **Releases/checks:** Immutable releases lock assets/tag upon publication and generate a release attestation. `gh release verify` is real, but verifies the **GitHub release attestation**, not npm approval, npm provenance or an honest test run. Use `verify-asset`/digest comparison for downloaded bytes. Required checks must apply to the relevant latest SHA; skipped/neutral conclusions can satisfy them. A dispatch check is not a universal substitute for PR checks. [Immutability][immutable], [CLI verification][gh-verify], [required checks][required-checks].
- **pnpm 11:** The published **11.28.6** archive confirms `allowBuilds`, `strictDepBuilds`, `blockExoticSubdeps`, `trustPolicy: no-downgrade`, and explicit `minimumReleaseAge` defaulting strictness to true. Its workspace validator permits missing `packages`; a settings-only file is valid for a root package. Build decisions may be explicit `false` as well as `true`; an empty map means unreviewed hooks fail under strict mode, not silently succeed. [Versioned archive][pnpm11-archive], [v11 release][pnpm11], [workspace settings][pnpm-settings], [build policy][pnpm-build].
- **Package verification:** publint **0.3.25** accepts a tarball pathname; this need not remain “verify” in the plan. Use `--strict` if warnings must fail CI. The existing SDK's `.js` relative import specifiers and type-only Standard Schema imports fit unbundled native `tsc` emission; core has no React imports. Existing unit/browser tests mainly import relative `src`, so they do not validate published exports. [Versioned publint CLI][publint], initial repository sources/tests.
- **Changesets prereleases:** Do not incorrectly criticize this plan using v2 behavior: v3.0.3 moves consumed prerelease change files into `.changeset/pre/`. A check for pending top-level changesets can work with that version. Use the CLI's parsing/state rather than rejecting every Markdown file recursively. [Versioned apply-release-plan][changeset-apply].

## 4. Simplification proposals

1. **Keep the root package for v1.** Add `tsconfig.build.json`, compiled exports, `files`, toolchain pin, CI and owned package name in place. A settings-only pnpm workspace already supplies dependency policy. Add a private docs directory later; root privacy is not a prerequisite for one safely publishable package. Postpone the large rename PR and associated synchronization cost.
2. **Keep the meaningful privilege split, reduce orchestration.** One dependency-running build/test/pack job and one clean stage-only OIDC job. Human downloads/inspects the recorded stage and approves on npm. Finalize via a small current-main recovery command or explicitly dispatched job; no extra environment click solely to communicate an event the registry can report.
3. **Make recovery explicit before making it automatic.** Start with a runbook using saved artifact/run ID plus registry SRI, and manual historical GitHub release repair when workflow permissions block it. Add verified provenance-derived automatic recovery only with fixtures for actual bundles, drafts, tag races and historical manifests. This is considerably more code/trust surface than “three plain Node scripts” suggests.
4. **Avoid a Cartesian test matrix.** At each PR, test the oldest supported TS with both resolution modes, current TS, core without React/types, React 18/19, supported Node import/require, and one browser bundler. Add broader TS/Node combinations when a compatibility bug justifies them. Retain real browser/polyfill tests and the tarball gate; they test distinct risks.
5. **Start docs with one visible version policy.** README/curated static docs with released version/SHA, or released docs plus an unreleased banner where needed. Add stable+next double builds only when a real prerelease train exists. Keep docs corrections possible without forcing an npm release; avoid introducing compiler plugins or a GitHub App initially.
6. **Make security claims proportionate.** npm approval is an independent *authorization boundary*, while the same maintainer's laptop/browser/passkey is still the root of trust. An extra self-approved GitHub gate adds little against that compromise. Avoid “no third-party code”: pinned setup/download actions, Node/npm and the hosted image remain trusted executable code; say “no repository dependencies or package lifecycle scripts in the stage job.”

## 5. Remaining unknowns and missing acceptance cases

- **Bootstrap/account reality:** ownership of the eventual scope, package settings/trust state, whether a staged-but-unapproved new name exposes trust configuration, and what exactly validates a stage-only configuration within its 48-hour window. Do not claim an end-to-end first-OIDC flow from documentation alone.
- **Independent approval evidence:** how the human obtains and compares staged bytes without trusting a potentially compromised build's summary. No file-diff script or approval runbook exists yet. Need a drill where the build changes a file **after** tests and regenerates its own manifest/hash.
- **Historical finalization:** explicit fixtures for absent tag+draft, tag+absent release, same-SHA draft with wrong assets, published release missing/wrong assets, concurrent conflicting tag creation, expired artifact, advanced manifest and changed workflow files. Published immutable releases with missing/wrong assets must fail, not silently no-op; rebuilding a manifest must not invent original test/run evidence.
- **Input/shell boundaries:** passing dispatch inputs through env is correct in the shown shell; there is no demonstrated input-injection exploit there. Future Node helpers must use `execFile`/argument arrays, strict validation and `--notes-file`, never shell interpolation of version/ref/changelog prose. Test quotes, backticks, `$()`, newlines, leading options and malicious release-note/summary Markdown. Allowlist tarball `publishConfig` keys as well as name/version: npm accepts configuration overrides there, including registry/provenance settings ([publish source][npm-publish]). Distinguish registry E404/ETARGET from transport/auth failures; only actual absence can select fresh mode.
- **Maintainer machine:** already acknowledged in README, but the recovery procedure should include revoking npm sessions, disabling affected trust configurations/Apps, securing both accounts and rejecting staged artifacts. GitHub/npm approvals on the same compromised device are not independent human review.
- **Dependabot and future Apps:** a Dependabot PR/update can carry malicious dependencies even when authored by the real bot; a version PR App adds write authority and its own key/installations. Treat their diffs and workflow/config changes as untrusted until reviewed; test effective permissions and never special-case a bot name into privileged execution. This is missing from the adversarial matrix.
- **Docs supply chain:** MDX/plugins and old-tag dependency installation execute code in the build job; a compromised builder can emit phishing/malicious static assets for the official origin without npm access. Explicitly include that artifact-integrity/branding risk, not just credential isolation. Verify exact host/ref/base behavior and a known-good rendered-artifact rollback.
- **Install policy practicality:** no pnpm 11 install was executed. Identify dependencies with hooks and record reasoned `false` denials or minimal `true` approvals; an “expected empty” map is not an acceptance result. Check frozen installs, age/trust handling and bot updates under the exact chosen patch, not only living v12 docs.
- **Support and inventory:** no compiler-floor/React-18/tarball-consumer run was performed here. The initial repo has real core/React tests but no build/release machinery; later shared-worktree edits must be re-inventoried before implementation. README prominently says unpublished prototype, so describing it as explicitly instructing users to *install* the unrelated npm package is overstated; import-name confusion remains a valid reason to rename.
