# A — Security and publishing research

Research cutoff and observation date: **2026-11-11**. Read-only research; no registry or GitHub settings were changed, no package was published, and no release commands were exercised. Sources below were fetched or searched on that date. “Verified” means documentation or a first-party release/advisory explicitly supports the statement; “inferred” means an engineering conclusion from that evidence; “unverified” marks an unresolved claim. Living docs can disagree with older CLI-version pages; those disagreements are preserved below.

## 1. npm trusted publishing, authentication, and approval

- **Verified — GA:** npm OIDC trusted publishing became generally available July 31, 2025, for public/private, scoped/unscoped packages. Source: [GA announcement](https://github.blog/changelog/2025-07-31-npm-trusted-publishing-with-oidc-is-generally-available/). Observed 2026-11-11; announcement 2025-07-31.
- **Verified — runtime floor:** npm CLI **11.5.1+**, Node **22.14.0+**. Source: [trusted publishers](https://docs.npmjs.com/trusted-publishers/). Observed 2026-11-11, current docs.
- **Verified — providers:** GitHub-hosted Actions runners, GitLab.com shared runners, CircleCI cloud; self-hosted runners remain unsupported. Source: [trusted publishers](https://docs.npmjs.com/trusted-publishers/). Observed 2026-11-11.
- **Verified — CircleCI:** added April 6, 2026, with website and `npm trust` configuration. Source: [CircleCI announcement](https://github.blog/changelog/2026-04-06-npm-trusted-publishing-now-supports-circleci/). Observed 2026-11-11; release 2026-04-06.
- **Verified — exact GitHub fields:** required organization/user, repository, workflow filename (basename, `.yml`/`.yaml`, under `.github/workflows/`); optional environment name. Matching is case-sensitive. Source: [trusted publishers](https://docs.npmjs.com/trusted-publishers/). Observed 2026-11-11.
- **Inferred — branch restriction:** npm’s documented GitHub configuration has no branch/ref field; constrain refs with GitHub environment deployment policies and workflow checks. Source: [trusted publishers](https://docs.npmjs.com/trusted-publishers/). Observed 2026-11-11; absence in documented schema, not a tested API rejection.
- **Verified — multiple publishers:** GA September 3, 2026; configurations are additive, any matching configuration authorizes, and evaluation order is unspecified. Every configuration can stage; direct publishing is opt-in for new configurations. Source: [multiple configurations](https://github.blog/changelog/2026-09-03-multiple-trusted-publishing-configurations-for-npm/). Observed 2026-11-11; release 2026-09-03.
- **Verified — maximum:** ten trusted publishers per package. Source: [trusted publishers](https://docs.npmjs.com/trusted-publishers/). Observed 2026-11-11.
- **Verified — validation window:** an unused configuration expires after 48 hours; first successful publication validates and binds repository identity. Recreate expired configurations. npm now rejects GitHub `issue_comment` and `pull_request_target` OIDC publishing. Source: [expiry announcement](https://github.blog/changelog/2026-10-02-unvalidated-npm-trusted-publishing-configurations-now-expire/). Observed 2026-11-11; release 2026-10-02.
- **Unverified — first-ever package publication:** no fetched primary documentation explicitly established a pending-publisher/package-name reservation flow. npm’s setup starts at existing package settings; staging is explicitly documented for existing packages. Treat manual/session-authenticated bootstrap as the conservative plan, **not a verified universal requirement**. Sources: [setup](https://docs.npmjs.com/trusted-publishers/), [existing-package staging prerequisite](https://github.blog/changelog/2026-09-18-stage-only-npm-tokens-for-safer-automation/). Observed 2026-11-11; no bootstrap attempted.
- **Verified — automatic provenance:** trusted publishing automatically attaches provenance for eligible GitHub/GitLab public-source/public-package releases; explicit `--provenance` is unnecessary. Private-source provenance remains unavailable. Source: [GA announcement](https://github.blog/changelog/2025-07-31-npm-trusted-publishing-with-oidc-is-generally-available/). Observed 2026-11-11; announcement 2025-07-31.
- **Verified — CircleCI exception:** CircleCI trusted publishing does not currently generate provenance. Source: [trusted publishers](https://docs.npmjs.com/trusted-publishers/). Observed 2026-11-11.
- **Verified — explicit provenance:** `npm publish --provenance` links a supported CI build to its package; `provenance-file` takes precedence over automatic generation. Sources: [provenance guide](https://docs.npmjs.com/generating-provenance-statements/), [CLI configuration](https://docs.npmjs.com/cli/v11/using-npm/config/). Observed 2026-11-11; npm v11 configuration docs.
- **Verified — publishing access:** package settings offer “Require two-factor authentication and disallow tokens”; trusted publishing remains the automation path. Source: [2FA publishing settings](https://docs.npmjs.com/requiring-2fa-for-package-publishing-and-settings-modification/). Observed 2026-11-11. This is distinct from merely enabling account 2FA.
- **Verified — current 2FA rule:** current npm docs say package creation/publication requires 2FA or a granular token with bypass enabled; settings changes require 2FA. Token-disallowing package policy overrides a granular token’s bypass flag. Source: [2FA publishing settings](https://docs.npmjs.com/requiring-2fa-for-package-publishing-and-settings-modification/). Observed 2026-11-11; page last edited 2026-08-03. OIDC is the documented CI alternative.
- **Verified — new-package defaults:** npm announced default 2FA enforcement for new publications in December 2025; interactive `npm login` now supplies a two-hour session with publishing 2FA. Source: [completed token transition](https://github.blog/changelog/2025-12-09-npm-classic-tokens-revoked-session-based-auth-and-cli-token-management-now-available/). Observed 2026-11-11; announcement 2025-12-09.
- **Verified — granular write tokens:** November 5, 2025 changes imposed 2FA by default, optional Bypass 2FA, and a 90-day maximum including existing write tokens (old expirations beyond February 3, 2026 were shortened). Source: [November token update](https://github.blog/changelog/2025-11-05-npm-security-update-classic-token-creation-disabled-and-granular-token-changes/). Observed 2026-11-11; release 2025-11-05.
- **Verified — original lifetime announcement:** new write tokens were announced with seven-day default and 90-day maximum. New TOTP setups were disabled in favor of WebAuthn/passkeys; existing TOTP was to be phased out. Source: [September security changes](https://github.blog/changelog/2025-09-29-strengthening-npm-security-important-changes-to-authentication-and-token-management/). Observed 2026-11-11; historical announcement, not proof of the final TOTP-removal date.
- **Verified — classic-token timeline correction:** creation was disabled November 5, 2025, but the definitive completion announcement says all classic tokens were permanently revoked **December 9, 2025**. Do not report the earlier planned November 19 deadline as the final observed completion date. Sources: [November plan](https://github.blog/changelog/2025-11-05-npm-security-update-classic-token-creation-disabled-and-granular-token-changes/), [December completion](https://github.blog/changelog/2025-12-09-npm-classic-tokens-revoked-session-based-auth-and-cli-token-management-now-available/). Observed 2026-11-11.
- **Verified — 2026 token governance:** bypass-2FA tokens cannot perform account identity/governance actions beginning August 2026; direct granular-token publishing is deprecated for removal in January 2027. Source: [access-token docs](https://docs.npmjs.com/about-access-tokens/). Observed 2026-11-11; January 2027 is future policy, not already enforced.
- **Verified — staged publishing exists:** GA in May 2026, npm **11.15.0+**. CI uploads a prebuilt artifact with `npm stage publish`; a human approves with 2FA before it becomes installable. Stage-only trust rejects direct `npm publish`. Source: [staged publishing GA](https://github.blog/changelog/2026-05-29-staged-publishing-and-new-install-time-controls-for-npm/). Observed 2026-11-11; article body dates release May 22, 2026 despite May 29 URL.
- **Verified — stage operations:** `publish`, `list`, `view`, `approve`, `reject`, `download`; publish defers 2FA, approval and rejection require it. Package write permission and an account with 2FA are prerequisites. Source: [npm stage CLI](https://docs.npmjs.com/cli/v12/commands/npm-stage/). Observed 2026-11-11; v12 docs.
- **Verified — approval scanning gate:** since September 3, approval is unavailable until malware scanning finishes; package versions expose staged/approved/rejected history to maintainers. Source: [September staging update](https://github.blog/changelog/2026-09-03-multiple-trusted-publishing-configurations-for-npm/). Observed 2026-11-11; release 2026-09-03.
- **Verified — stage-only tokens are narrower only for new-version publication:** introduced September 18, 2026; they still move dist-tags and deprecate versions. Source: [stage-only tokens](https://github.blog/changelog/2026-09-18-stage-only-npm-tokens-for-safer-automation/). Observed 2026-11-11; release 2026-09-18.
- **Verified — bulk trust management:** `npm trust` became GA with npm **11.10.0+** on February 18, 2026; this reduces per-package UI work in a monorepo. Source: [bulk trust announcement](https://github.blog/changelog/2026-02-18-npm-bulk-trusted-publishing-config-and-script-security-now-generally-available/). Observed 2026-11-11.
- **Verified — pnpm v10 uses npm:** v10.14.0 source packs then invokes `runNpm(opts.npmPath, ['publish', ...])`; its OIDC capability depends on the selected npm CLI and environment. Source: [versioned publish implementation](https://github.com/pnpm/pnpm/blob/v10.14.0/releasing/plugin-commands-publishing/src/publish.ts). Observed 2026-11-11; source v10.14.0.
- **Inferred — pnpm v10 OIDC support:** v10.14.0 plus a working npm 11.5.1+ is an evidenced combination; there is no independently verified “first pnpm OIDC version” here. Packing with pnpm and explicitly publishing that tarball using compatible npm avoids ambiguity. Sources: [v10 implementation](https://github.com/pnpm/pnpm/blob/v10.14.0/releasing/plugin-commands-publishing/src/publish.ts), [npm floor](https://github.blog/changelog/2025-07-31-npm-trusted-publishing-with-oidc-is-generally-available/). Observed 2026-11-11; inference, not execution.
- **Verified — native pnpm support now exists:** October 2026 releases explicitly fix OIDC handling in `pnpm publish`; v12.12.1 adds OIDC `dist-tag`, while v11.28.6 fixes CI-token registry audience handling. Sources: [release index](https://pnpm.io/blog?type=releases), [v11.28.6 context](https://pnpm.io/blog/). Observed 2026-11-11; current support verified, earliest native OIDC version unresolved.
- **Verified — pnpm staging:** `pnpm stage` arrived in **11.3**, including download/approval/rejection. Source: [pnpm 11.3](https://pnpm.io/blog/releases/11.3). Observed 2026-11-11; release 2026-05-24 per release index.

## 2. npm immutability and recovery

- **Verified — immutable name/version:** a published `name@version` cannot be overwritten or reused, even after unpublish. Source: [unpublish policy](https://docs.npmjs.com/policies/unpublish/). Observed 2026-11-11.
- **Verified — first 72 hours:** newly created packages can be unpublished within 72 hours only if no public-registry package depends on them. Source: [unpublish policy](https://docs.npmjs.com/policies/unpublish/). Observed 2026-11-11.
- **Verified — after 72 hours:** all three conditions must hold: no public-registry dependents, fewer than 300 weekly downloads, and one owner/maintainer. Whole-package removal also imposes a 24-hour wait before publishing a new version. Source: [unpublish policy](https://docs.npmjs.com/policies/unpublish/). Observed 2026-11-11.
- **Verified — deprecate:** retains downloadable versions but adds warnings; `npm deprecate package@version "message"` is a recovery option when unpublish is unavailable. Source: [unpublish policy](https://docs.npmjs.com/policies/unpublish/). Observed 2026-11-11.
- **Verified — tag mutation:** `npm dist-tag add package@version tag` creates/repoints a tag; `rm package tag` removes the mapping; `ls` lists mappings. Publish uses `latest` by default; tag names cannot parse as semver ranges. Source: [dist-tag CLI](https://docs.npmjs.com/cli/v12/commands/npm-dist-tag/). Observed 2026-11-11; v12 docs.
- **Verified — tags are not package bytes:** moving `latest` changes future tag-based resolution, without overwriting any version. Source: [dist-tag CLI](https://docs.npmjs.com/cli/v12/commands/npm-dist-tag/). Observed 2026-11-11.
- **Verified — OIDC can change tags now:** GA September 30, 2026; enable `Allow npm dist-tag` separately for each trust configuration. Default off for both existing/new configurations; stage/direct-publish permission alone is insufficient. Source: [OIDC dist-tag announcement](https://github.blog/changelog/2026-09-30-opt-in-dist-tag-permissions-for-npm-trusted-publishing/). Observed 2026-11-11.
- **Verified — dist-tag CLI floors:** npm **11.21.0+ on v11**, **12.2.0+ on v12**; public tag reads need no authentication. Source: [trusted publishers, dist-tags](https://docs.npmjs.com/trusted-publishers/). Observed 2026-11-11.
- **Verified — current documentation conflict:** `npm stage` CLI docs still describe trust credentials as limited to stage/publish, while newer trusted-publisher docs and September 30 announcement explicitly permit opt-in tag operations. Prefer the newer operation-specific release and required CLI floors. Sources: [stage CLI](https://docs.npmjs.com/cli/v12/commands/npm-stage/), [dist-tag release](https://github.blog/changelog/2026-09-30-opt-in-dist-tag-permissions-for-npm-trusted-publishing/). Observed 2026-11-11.
- **Inferred — rollback:** deprecate a bad version and repoint a channel to a previously good immutable version; publish a new fix version when needed. This cannot recall tarballs already downloaded or force consumers with lockfiles to change. Sources: [unpublish policy](https://docs.npmjs.com/policies/unpublish/), [dist-tag CLI](https://docs.npmjs.com/cli/v12/commands/npm-dist-tag/). Observed 2026-11-11.

## 3. GitHub Actions security and repository controls

### Environments, identity, and permissions

- **Verified — environment review:** up to six users/teams, at least read access, **one** approval sufficient. Prevent-self-review blocks the initiating user from approving. Source: [deployments and environments](https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments). Observed 2026-11-11.
- **Verified — availability:** required reviewers and wait timers work on public repositories under Free/Pro/Team; branch/tag policies are available for all public repositories. Source: [environment reference](https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments). Observed 2026-11-11.
- **Verified — timer:** 1–43,200 minutes, unbilled waiting. Administrators can bypass protection by default; disabling bypass is configurable. Source: [environment reference](https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments). Observed 2026-11-11.
- **Verified — deployment refs:** selected branch/tag patterns are evaluated against `GITHUB_REF`; branch and tag patterns are separate, `*` does not cross `/`. “Protected branches only” allows all branches if no protections exist. Source: [environment reference](https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments). Observed 2026-11-11.
- **Inferred — solo maintainer:** prevent-self-review needs another eligible human; otherwise a maintainer-triggered release cannot be approved by that same maintainer. Source: [environment reference](https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments). Observed 2026-11-11.
- **Verified — traditional OIDC subjects:** environment jobs use `repo:ORG/REPO:environment:NAME`; without environment, PRs use `repo:ORG/REPO:pull_request`, otherwise branch/tag forms use `repo:ORG/REPO:ref:refs/heads/BRANCH` or `...:refs/tags/TAG`. Source: [OIDC reference](https://docs.github.com/en/actions/reference/security/oidc). Observed 2026-11-11.
- **Verified — July 2026 identity change:** new repositories after July 15, 2026 use names plus immutable IDs, e.g. `repo:OWNER@OWNER-ID/REPO@REPO-ID:ref:refs/heads/main`. Older repositories retain legacy subjects unless opted in; later renames/transfers migrate. Source: [OIDC reference](https://docs.github.com/en/actions/reference/security/oidc). Observed 2026-11-11.
- **Verified — reusable identity:** `job_workflow_ref` and `job_workflow_sha` identify reusable workflows; `workflow_ref`, `workflow_sha`, `ref`, repository IDs and runner environment are additional claims. These claims do not imply npm exposes every one as a trust setting. Source: [OIDC reference](https://docs.github.com/en/actions/reference/security/oidc). Observed 2026-11-11.
- **Verified — least privilege:** use read-only repository defaults and elevate specific jobs. OIDC issuance needs `id-token: write`; ordinary checkout uses `contents: read`. Source: [secure-use reference](https://docs.github.com/en/actions/reference/security/secure-use), [OIDC reference](https://docs.github.com/en/actions/reference/security/oidc). Observed 2026-11-11.
- **Verified — attestation permissions:** GitHub artifact attestation example needs `id-token: write`, `contents: read`, `attestations: write`; the last permission is for GitHub attestations, not a general npm OIDC requirement. Source: [attestation guide](https://docs.github.com/en/actions/how-tos/secure-your-work/use-artifact-attestations/use-artifact-attestations). Observed 2026-11-11.
- **Verified — token default:** new personal-account repositories default `GITHUB_TOKEN` to read-only contents/packages; organization repositories inherit organization defaults. Existing repositories must be inspected rather than assumed safe. Source: [Actions settings](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/enabling-features-for-your-repository/managing-github-actions-settings-for-a-repository). Observed 2026-11-11.

### Rules, dependency policies, and review

- **Verified — rulesets:** public repositories on GitHub Free support branch/tag rulesets, with layered enforcement and explicit bypass actors. Source: [about rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/about-rulesets). Observed 2026-11-11.
- **Verified — release tags:** rulesets can restrict creation, updates and deletion of matching refs; permitted bypass actors must be chosen deliberately. These are distinct rules, not a single “protect tag” switch. Source: [available rules](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets). Observed 2026-11-11.
- **Verified — status gating:** rulesets can require status checks and PR approval before merge. Check source restrictions can bind expected checks to a GitHub App. Source: [available rules](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets). Observed 2026-11-11.
- **Verified — merge queue account limit:** public repositories must be **organization-owned**; personal-account public repositories are not included. Private availability requires organization Enterprise Cloud. Actions checks must handle `merge_group`. Source: [merge queue](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue). Observed 2026-11-11.
- **Verified — immutable releases:** GA October 28, 2025. New immutable releases lock assets against adding/modifying/deleting and lock associated tags against moving/deleting; disabling the setting does not unlock existing immutable releases. Existing mutable releases are not converted automatically. Source: [GA announcement](https://github.blog/changelog/2025-10-28-immutable-releases-are-now-generally-available/). Observed 2026-11-11.
- **Verified — release attestations:** immutable releases carry signed Sigstore-format attestations; CLI verification includes `gh release verify` / `gh release verify-asset`. Sources: [GA announcement](https://github.blog/changelog/2025-10-28-immutable-releases-are-now-generally-available/), [preview CLI examples](https://github.blog/changelog/2025-08-26-releases-now-support-immutability-in-public-preview/). Observed 2026-11-11.
- **Inferred — release assembly order:** upload all intended assets while draft, then publish immutable release. Otherwise immutability prevents adding the missing artifact later. Source: [immutable-release behavior](https://github.blog/changelog/2025-10-28-immutable-releases-are-now-generally-available/). Observed 2026-11-11.
- **Verified — SHA policy exists:** repository Actions permissions REST API exposes `sha_pinning_required: boolean`, alongside `allowed_actions: all|local_only|selected`. Source: [REST permissions](https://docs.github.com/en/rest/actions/permissions). Observed 2026-11-11; API docs examples use 2026-03-10.
- **Verified — allowed-action policy:** SHA enforcement and explicit action blocklists shipped August 15, 2025; `!` entries override allow entries. Source: [policy release](https://github.blog/changelog/2025-08-15-github-actions-policy-now-supports-blocking-and-sha-pinning-actions/). Observed 2026-11-11.
- **Verified — newer lockfiles:** current GitHub guidance prefers workflow dependency lockfiles that record exact commits, including transitive actions, and verify source repository identity at runtime. Source: [workflow dependency lockfiles](https://docs.github.com/en/actions/concepts/security/workflow-dependency-lockfiles). Observed 2026-11-11. Tooling adoption/version compatibility still needs implementation review.
- **Verified — CODEOWNERS:** own `.github/workflows/` and the CODEOWNERS file itself, and require code-owner reviews via protection/rulesets; ownership alone only requests review. Source: [code owners](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-code-owners). Observed 2026-11-11.
- **Verified — fork approvals:** default is first-time contributors; alternatives include newcomers to GitHub only or all external contributors. A previously merged innocuous contribution can bypass first-time-only gating. Source: [Actions settings](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/enabling-features-for-your-repository/managing-github-actions-settings-for-a-repository). Observed 2026-11-11.

### Untrusted execution, caches, and artifacts

- **Verified — pwn requests:** checking out/building attacker-controlled PR code under `pull_request_target` exposes privileged context; malicious package scripts/tests are sufficient execution paths. Source: [GitHub Security Lab](https://securitylab.github.com/resources/github-actions-preventing-pwn-requests/). Observed 2026-11-11; article 2021-08-03, reaffirmed by current docs.
- **Verified — workflow_run:** privileged follow-up workflows must distrust incoming artifacts and avoid executing untrusted PR contents. Source: [secure-use reference](https://docs.github.com/en/actions/reference/security/secure-use). Observed 2026-11-11.
- **Verified — script injection:** do not embed untrusted `${{ github.event... }}` text directly in generated shell; pass it through an action argument or intermediate environment variable and quote shell variables. Source: [secure-use reference](https://docs.github.com/en/actions/reference/security/secure-use). Observed 2026-11-11.
- **Verified — branch cache scope:** runs restore current/default branch caches, PRs also base-branch caches; normal PR-created caches belong to merge refs and cannot be restored by main. Never place credentials in caches accessible to forks. Source: [cache reference](https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching). Observed 2026-11-11.
- **Verified — newer cache hardening:** default-branch runs from low-trust triggers including `pull_request_target`, `issue_comment`, `workflow_run` now get read-only default-branch cache access unless explicitly overridden by write-capable `cache-mode`. Source: [cache reference](https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching). Observed 2026-11-11; historical incidents predate these defaults.
- **Verified — cache kill switch:** `cache-mode: none` at workflow/job scope disables cache access, honored by `actions/cache` and its toolkit. This is stronger than merely removing one visible cache step. Source: [cache reference](https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching). Observed 2026-11-11.
- **Verified — setup-node:** uses `actions/cache` for package-manager data, does not cache `node_modules`; npm caching can be automatic from `packageManager`, disabled by `package-manager-cache: false`. Explicit pnpm caching uses `cache: pnpm`. Source: [setup-node README](https://github.com/actions/setup-node). Observed 2026-11-11; README examples currently v7.
- **Verified — artifacts v4:** immutable uploaded artifacts, unique names needed for separate uploads; overwrite deletes/recreates rather than mutating the same artifact. Upload exposes SHA-256 digest. Source: [upload-artifact](https://github.com/actions/upload-artifact). Observed 2026-11-11; v4 behavior documented in current README.
- **Verified — artifact digest validation:** download computes and compares digest and warns on mismatch. A warning is not a release policy rejecting an untrusted producer. Source: [artifact storage and validation](https://docs.github.com/en/actions/how-tos/writing-workflows/choosing-what-your-workflow-does/storing-and-sharing-data-from-a-workflow). Observed 2026-11-11; digest enforcement behavior should be tested before relying on it as a gate.
- **Verified — attestation action rename:** `actions/attest-build-provenance` v4 is a wrapper around `actions/attest`; existing users can continue, new implementations should use `actions/attest`. Source: [upstream README](https://github.com/actions/attest-build-provenance). Observed 2026-11-11; current README.
- **Verified — verification command:** `gh attestation verify PATH -R OWNER/REPO`; SBOM predicates require `--predicate-type`. Source: [GitHub attestations](https://docs.github.com/en/actions/how-tos/secure-your-work/use-artifact-attestations/use-artifact-attestations). Observed 2026-11-11.

## 6. Relevant supply-chain incidents, 2024–2026

Counterfactual controls below are **inferences**, not claims that one control would defeat every variant of an incident.

- **Verified incident / inferred control — 2024 filename injection:** GitHub Security Lab’s January 12, 2024 advisory shows attacker-chosen filenames flowing into `${{ steps...outputs... }}` in shell, producing command execution. Pass data through quoted variables/structured arguments; avoid generated shell interpolation. Source: [GHSL-2023-271](https://securitylab.github.com/advisories/GHSL-2023-271_changed-files/). Observed 2026-11-11; tested changed-files v40.2.2.
- **Verified incident / inferred control — tj-actions, March 14, 2025:** compromised bot PAT, retroactively retargeted version tags, runner-memory secrets exposed in public logs. Pin a verified clean full commit and constrain transitive Actions; remove unnecessary secrets, revoke credentials after exposure. OIDC does not make a compromised running job safe. Source: [StepSecurity investigation](https://www.stepsecurity.io/blog/harden-runner-detection-tj-actions-changed-files-action-is-compromised). Observed 2026-11-11; original responder report 2025-03-14, CVE-2025-30066.
- **Verified incident / inferred control — reviewdog, March 11, 2025:** malicious `action-setup@v1` retagging affected downstream composite actions. Pinning only the top-level action leaves floating transitive references exposed; use dependency locking/audit. Source: [StepSecurity reviewdog report](https://www.stepsecurity.io/blog/reviewdog-github-actions-are-compromised). Observed 2026-11-11; reported compromise window 18:42–20:31 UTC.
- **Verified incident / inferred control — Nx s1ngularity, August 26, 2025:** workflow injection stole npm publishing token; malicious postinstall scanned secrets, used local AI tools and exfiltrated to public GitHub repositories. Nx adopted trusted publishing and manual release approval. Eliminate vulnerable interpolation, block unapproved hooks, remove reusable publish tokens. Source: [Nx first-party postmortem](https://nx.dev/blog/s1ngularity-postmortem). Observed 2026-11-11; postmortem 2025-09-05.
- **Verified incident / inferred control — chalk/debug, September 8, 2025:** maintainer phishing/account takeover pushed browser-runtime crypto-address interception. Install-hook blocking alone would not stop runtime payloads; release age, phishing-resistant account auth, OIDC-only publication and review narrow entry paths. Source: [Socket incident summary](https://socket.dev/glossary/npm-security). Observed 2026-11-11; retrospective security-research source, not maintainer postmortem.
- **Verified incident / inferred control — Shai-Hulud, September 2025:** npm account compromise plus malicious postinstall, credential theft and self-replication; GitHub reports removal of 500+ compromised packages. Restrict install hooks, isolate build credentials and disallow token publishing; age gates reduce early exposure. Source: [GitHub first-party response](https://github.blog/security/supply-chain-security/our-plan-for-a-more-secure-npm-supply-chain/). Observed 2026-11-11; GitHub notified 2025-09-14.
- **Verified incident / inferred control — Shai-Hulud 2.0, November 24, 2025 onward:** worm harvested secrets and persisted beyond initial containment; leaked credentials required rotation, not just deleting packages. Age delays and script restrictions help initial ingestion; clean IDE extensions/mirrors and revoke all exposed credentials for recovery. Sources: [Wiz incident response](https://www.wiz.io/blog/shai-hulud-2-0-aftermath-ongoing-supply-chain-attack), [long-tail investigation](https://www.wiz.io/blog/snipping-the-long-tail-of-shai-hulud-2-0). Observed 2026-11-11; reports 2025-12-01 and 2025-12-30.
- **Verified incident / inferred control — axios, March 31, 2026:** maintainer postmortem describes social engineering/account compromise; malicious releases were distributed through npm. Removing alternate token/session publishing paths limits bypass of protected CI; dependency-age delay helps consumers. Source: [axios first-party postmortem](https://github.com/axios/axios/issues/10636). Observed 2026-11-11; investigation details may evolve; do not characterize the exact credential as a classic token revoked in 2025.
- **Verified incident / inferred control — TanStack, May 11, 2026:** first-party postmortem attributes 84 malicious versions across 42 packages to `pull_request_target`, cross-trust cache poisoning and extraction of a live OIDC token from runner memory. Disable release cache access, isolate privileged jobs, eliminate untrusted privileged execution, and use npm stage-only approval. Source: [TanStack postmortem](https://tanstack.com/blog/npm-supply-chain-compromise-postmortem). Observed 2026-11-11; incident 2026-05-11. Direct evidence that tokenless publication is not malware prevention.
- **Verified incident / inferred control — Red Hat Miasma, May/June 2026:** Microsoft researchers describe upstream CI compromise distributing modified `@redhat-cloud-services` packages through legitimate GitHub Actions OIDC publishing, with credential-stealing preinstall/persistence. Review source and workflow authority, restrict installation execution, and independently approve staged artifacts. Source: [Microsoft Defender research](https://www.microsoft.com/en-us/security/blog/2026/06/02/preinstall-persistence-inside-red-hat-npm-miasma-credential-stealing-campaign/). Observed 2026-11-11; report 2026-06-02.

## 7. SBOM, signatures, provenance, and verification

- **Verified — npm provenance:** build provenance identifies source/build environment; a publish attestation is generated by the registry for an authorized publication. These are evidence of origin, not code review or malware-free certification. Source: [npm provenance](https://docs.npmjs.com/generating-provenance-statements/). Observed 2026-11-11.
- **Verified — Sigstore role:** identity-based short-lived signing credentials and transparency infrastructure enable artifact-signature/attestation verification without maintainers managing a permanent signing key. Source: [Sigstore overview](https://docs.sigstore.dev/about/overview/). Observed 2026-11-11; living docs.
- **Inferred — separate artifacts:** GitHub/Sigstore attestations on a `.tgz`, npm registry provenance, and GitHub immutable-release attestations serve related but distinct verification paths. Attest the exact bytes actually published, not a separately rebuilt archive. Sources: [GitHub attestations](https://docs.github.com/en/actions/how-tos/secure-your-work/use-artifact-attestations/use-artifact-attestations), [npm provenance](https://docs.npmjs.com/generating-provenance-statements/). Observed 2026-11-11.
- **Verified — SBOM command:** `npm sbom --sbom-format=spdx` or `--sbom-format=cyclonedx` inventories project dependencies; `--package-lock-only` reads a lockfile rather than installed tree. Source: [npm sbom](https://docs.npmjs.com/cli/v12/commands/npm-sbom/). Observed 2026-11-11; page selector v12.2.2.
- **Inferred — pnpm SBOM fit:** do not generate an unrelated npm lockfile merely to satisfy an npm SBOM recipe; use the installed artifact/dependency graph or evaluate native `pnpm sbom` in the pinned pnpm version. Source: [npm sbom](https://docs.npmjs.com/cli/v12/commands/npm-sbom/), [pnpm 11 release](https://github.com/pnpm/pnpm/releases/tag/v11.0.0). Observed 2026-11-11; pnpm v11 release lists native SBOM command.
- **Verified — consumer verification:** `npm audit signatures` verifies registry signatures and available provenance attestations; `--json --include-attestations` can return verified Sigstore bundles. This is separate from advisory vulnerability auditing. Source: [npm audit](https://docs.npmjs.com/cli/v12/commands/npm-audit/). Observed 2026-11-11; current v12 docs.
- **Unverified — adoption:** no reliable measurement found for what fraction of consumers verify attestations or enforce identity policies. Availability of verification commands does not establish their use, and signatures alone do not establish package safety. Sources: [npm audit](https://docs.npmjs.com/cli/v12/commands/npm-audit/), [Sigstore overview](https://docs.sigstore.dev/about/overview/). Observed 2026-11-11.

Source: [scorecard-action](https://github.com/ossf/scorecard-action). Observed 2026-11-11; current upstream README.
- **Inferred — Scorecard limit:** useful periodic posture signal, not a release-artifact malware scan or proof of a particular SLSA level. Source: [scorecard-action](https://github.com/ossf/scorecard-action). Observed 2026-11-11.

## Implications for a small library

- **Inferred — choose stage-only OIDC:** npm’s human 2FA approval provides an independent registry-side checkpoint; direct OIDC remains an explicit convenience/security tradeoff. Source: [staging GA](https://github.blog/changelog/2026-05-29-staged-publishing-and-new-install-time-controls-for-npm/). Observed 2026-11-11.
- **Inferred — remove alternate credentials:** enable token-disallowing publication policy once OIDC works and revoke obsolete write tokens. Source: [2FA publishing settings](https://docs.npmjs.com/requiring-2fa-for-package-publishing-and-settings-modification/). Observed 2026-11-11.
- **Inferred — pin tools deliberately:** exact pnpm version in `packageManager`, reviewed Actions digests/lockfile, and explicit compatible npm/Node versions reduce surprise upgrades. Sources: [Corepack](https://github.com/nodejs/corepack), [workflow lockfiles](https://docs.github.com/en/actions/concepts/security/workflow-dependency-lockfiles). Observed 2026-11-11.
- **Inferred — isolate authority:** ordinary PR CI should have no publish identity; only a short release job receives OIDC and a matching environment. Source: [secure use](https://docs.github.com/en/actions/reference/security/secure-use). Observed 2026-11-11.
- **Inferred — avoid release caches:** use `cache-mode: none`, disable setup-node automatic caching, and audit helper actions for hidden cache use. Source: [cache reference](https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching). Observed 2026-11-11.
- **Inferred — guard inputs and refs:** enforce protected source review and release-tag rules, bind npm trust to the environment, validate release commit/version/tag consistency. Sources: [rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets), [environments](https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments). Observed 2026-11-11.
- **Inferred — account for solo operation:** independent environment reviewers are useful only with another maintainer; registry staging still offers intentional 2FA presence for a solo maintainer. Sources: [environments](https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments), [staging](https://docs.npmjs.com/staged-publishing/). Observed 2026-11-11.
- **Inferred — explicit dependency defenses:** frozen lockfile, narrow build allowlist, strict builds, age delay, exotic-subdependency blocking; consider no-downgrade with narrow documented exceptions. Sources: [pnpm build settings](https://pnpm.io/settings/build), [dependency resolution](https://pnpm.io/settings/dependency-resolution). Observed 2026-11-11.
- **Inferred — inspect shipped bytes:** pnpm-pack once, inspect included files/manifest, smoke-test installation of that archive, then stage the same archive. Source: [pnpm pack](https://pnpm.io/cli/pack). Observed 2026-11-11.
- **Inferred — lean update automation:** one updater, grouped routine updates, explicit age delay, required checks; manual review of release machinery. Sources: [Renovate configuration](https://docs.renovatebot.com/configuration-options/), [Dependabot automation](https://docs.github.com/en/code-security/tutorials/secure-your-dependencies/automate-dependabot-with-actions). Observed 2026-11-11.
- **Inferred — lint workflows:** actionlint for correctness, zizmor for security, scheduled Scorecard for settings drift; review suppressions as code. Sources: [actionlint](https://github.com/rhysd/actionlint), [zizmor audits](https://docs.zizmor.sh/audits/), [Scorecard](https://github.com/ossf/scorecard-action). Observed 2026-11-11.
- **Inferred — publish usable evidence:** retain exact tarballs and checksums, eligible npm provenance, optional SBOM/GitHub attestations, and immutable GitHub release assets. Sources: [npm provenance](https://docs.npmjs.com/generating-provenance-statements/), [immutable releases](https://github.blog/changelog/2025-10-28-immutable-releases-are-now-generally-available/). Observed 2026-11-11.
- **Inferred — tokenless channel promotion:** grant dist-tag permission only to workflows that actually promote/roll back; it is no longer necessary to retain a token solely for tag updates. Source: [dist-tag OIDC release](https://github.blog/changelog/2026-09-30-opt-in-dist-tag-permissions-for-npm-trusted-publishing/). Observed 2026-11-11.
- **Inferred — recovery playbook:** revoke exposed credentials, deprecate bad versions, move tags, publish a new fixed version; purge poisoned caches and assess developer machines. Sources: [npm policy](https://docs.npmjs.com/policies/unpublish/), [Wiz long tail](https://www.wiz.io/blog/snipping-the-long-tail-of-shai-hulud-2-0). Observed 2026-11-11.
